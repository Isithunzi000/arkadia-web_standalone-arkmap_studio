1. Overview

The .arkdelta format is a JSON-based edit delta format for Arkadia MUD maps. It records a sequence of editing operations performed in ArkMap Studio on top of a known base map version, so the same set of changes can be re-applied later onto a newer upstream map release.

The typical workflow: a user downloads a map, makes local fixes in edit mode, and saves them as a .arkdelta file ("overlay" / kalka). When a fresh map version is released, the user downloads it, loads the overlay, and the changes are re-applied onto the new base.

Key design goals:

  • Deterministic — the same edit log always produces a byte-identical file (canonical serialization, sorted keys, CRC-32 checksums)
  • Anonymous additions — rooms, areas and labels created by the delta carry no numeric IDs in the file; they use symbolic IDs (d:N) and receive fresh numbers on apply, like an overlay
  • Fail-closed — a corrupted or tampered file is refused outright, with precise diagnostics; nothing is loaded
  • Non-destructive — applying a delta goes through the normal undo machinery: every applied operation enters the undo history as a regular edit, and undo/redo behavior is unchanged
  • Self-describing base — the file records the identity (file checksum) of the map variant it was created from, plus optional version/revision metadata
Relationship to .arkmap: A delta never stores a full map — only operations. The base identity is the hierarchical file checksum of the .arkmap canonical form of the map that was loaded when the edits were made (including the reduced-information variant derived from a Mudlet .dat file, where base identity is the file checksum of that derived .arkmap form). The checksum algorithm is the one defined by the .arkmap spec (currently v3 — XXH3-64, 16-hex); deltas written against older map checksum generations (CRC-32, 8-hex) never match re-saved maps, so the base gate always reports a mismatch for them (informational dialog — the user may continue; see §4 and §9).

2. Top-Level Structure

{
  "meta":      { ... },   // REQUIRED — format marker, base identity, bookkeeping (see §3)
  "ops":       [ ... ],   // REQUIRED — ordered array of operation objects (see §7)
  "checksums": { ... }    // REQUIRED — CRC-32 checksums (see §5)
}

Keys at every level are serialized in sorted order (see §5). The file is produced by buildDelta() from the editor's full edit log and consumed by validateDeltaText() + applyDelta().

4. Base Identity

meta.base identifies the map variant the delta was created against:

FieldTypeReqDescription
crcstringREQFile checksum (hex) of the canonical .arkmap form of the base map — the hierarchical file checksum as defined by the .arkmap spec §15 (algorithm v3: XXH3-64, 16 lowercase hex characters)
versionstringOPTMap version, copied from meta.user_data.version when present
revisionstringOPTSource revision (commit SHA), copied from meta.user_data.revision when present

The base checksum is computed once, at map load time — not at export time. The computation clones the loaded map, sorts areas/rooms/labels by id, sorts per-room array fields (stubs, exit_locks, special_exit_locks), drops the internal room.area field, and takes the hierarchical meta.checksums.file of the clone. This makes the identity independent of in-memory ordering and of transient editing state.

Why at load: the base identity must describe the map the user started from, not the map after edits. Computing it at load keeps it stable no matter what the session does afterwards.

On load of a delta, the application compares base.crc with the identity of the currently loaded map and informs the user whether the base matches ("baza zgodna") or differs ("kalka z innej wersji mapy"). A mismatch is not an error — applying onto a newer upstream version is the primary use case.

5. Canonical Serialization & Checksums

The file is serialized with the same canonical JSON writer as .arkmap (stableStringify): object keys sorted lexicographically at every level, no insignificant whitespace beyond the fixed pretty-print layout, UTF-8 encoding. The full canonical rules are those of the .arkmap specification (§16) — in particular, arrays of primitives with at most 8 elements are written inline on a single line (e.g. [255, 0, 0]), arrays of objects use the standard multi-line layout, and undefined values are omitted.

Checksums use CRC-32 (hex string, lowercase) over the canonical serialization:

FieldTypeDescription
checksums.filestringCRC-32 of the canonical form of { meta, ops } (the whole file minus the checksums object itself)
checksums.opsarray<string>Per-operation CRC-32 of the canonical form of each op, in order; used to localize corruption
Tamper handling: if checksums.file does not match, the file is refused. The per-op checksums are then used to name the offending operations precisely (e.g. „op #17, #23 nie zgadza się z sumą kontrolną"). The per-op array is diagnostic only — it is not itself an integrity gate.

6. Symbolic IDs (sid)

Objects created by the delta (rooms, areas, labels) do not exist in the base map, so they have no meaningful numeric IDs. In the file they are identified by symbolic IDs:

sid := "d:" N        // N ≥ 1, decimal, no leading zeros — regex: /^d:[1-9][0-9]*$/

Rules:

  • Single global counter — sids are assigned from one counter shared across object kinds, in edit-log order (d:1, d:2, …). The file stays readable and sids never collide across kinds.
  • Define-before-use — a sid is defined by its ADD_ROOM / ADD_AREA / ADD_LABEL operation and may be referenced only by later operations. This holds by construction (the editor cannot reference an object that does not exist yet) and is enforced by validation.
  • Liveness — a sid is live from its ADD until the matching DELETE. Because the editor allocates numeric IDs as max+1 of the current state, deleting an object and adding a new one may reuse the same session numeric ID — each such incarnation gets a fresh sid. A sid therefore denotes one live object instance, never a number.
  • No duplicates — two ADD operations defining the same sid make the file invalid.
  • Reference rewriting — everywhere a room ID appears in an operation (exits, special_exits, exit targets, source rooms, snapshots), a sid-created ID is written as its sid. Label sids follow the same rule inside their parent area; area sids likewise.

On apply, each sid receives a fresh numeric ID from a monotonically increasing counter starting at max(existing IDs)+1 (per area for labels), and every reference is translated through the sid map.

7. Operations

Each entry in ops:

{
  "seq":     1,          // REQUIRED — 1-based, contiguous, in application order
  "type":    "ADD_ROOM", // REQUIRED — one of the 25 operation types below
  "target":  { ... },     // REQUIRED — object identity the op applies to
  "payload": { ... },     // REQUIRED — operation data
  "label":   "..."        // REQUIRED (may be "") — human-readable description, as in undo history
}

Room objects embedded in payloads (e.g. ADD_ROOM.payload.room) follow the .arkmap omission convention: empty containers and default values are omitted, and the internal area field never appears.

8. Validation Rules

Validation is fail-closed: any violation refuses the whole file with a list of diagnostics; nothing is loaded. Checks run in this order:

  1. Size limit — file larger than 8 MiB is refused.
  2. JSON — the file must parse as a single JSON object.
  3. Magic — meta.format must be "arkdelta".
  4. Version — meta.format_version must equal 1 (an unknown version advises updating ArkMap Studio).
  5. File checksum — checksums.file must match the canonical form of { meta, ops }; on mismatch, per-op checksums localize the corrupted operations by seq.
  6. Operation count — at most 5000 operations; meta.ops_count must equal ops.length.
  7. Sequence — seq values must be 1-based and contiguous.
  8. Schema — type must be one of the 25 known types; target/payload must be objects carrying the required fields per type (§7).
  9. Directions — any target.dir must be a valid direction (n, ne, e, se, s, sw, w, nw, up, down, in, out).
  10. Key sanitization — the keys __proto__, constructor, prototype are forbidden anywhere in an operation.
  11. sid integrity — define-before-use and no duplicate definitions (§6).

9. Apply Semantics

Applying a delta replays the operations in seq order onto the currently loaded map:

  • Translation — each op is deep-cloned and every known sid is replaced by its fresh numeric ID (§6). A defensive scan afterwards refuses any op that still contains an unknown sid reference (other than the sid the op itself defines).
  • Fresh IDs — rooms and areas are numbered from max(existing)+1 with monotonic counters; labels from max+1 within their area.
  • Execution — where the editor has a programmatic commit with its own guards (deleteRoom, commitDeleteArea, commitMoveRoomToArea, commitAddExit, commitMoveRoom, commitDeleteExit), the apply path calls it, so guard refusals behave exactly as in interactive editing (e.g. ADD_EXIT onto an occupied direction, or DELETE_AREA targeting the default area — areaId ≤ 0 is always skipped with a reason, the default area cannot be deleted). Remaining types are executed by reconstructing the equivalent undo entry and dispatching it through the same redo machinery used by undo/redo replay.
  • Per-op isolation — every op runs in its own try/catch. An op that cannot be applied (missing target room/area/label, occupied direction, guard refusal, execution error) is skipped with a reason and does not stop later ops. The result is reported as { applied, appliedSeqs, skipped: [{ seq, reason }] }, where appliedSeqs lists the seq numbers actually applied — the review panel uses them to mark the layer „naniesione z tej kalki” (applied from this overlay).
  • Undo integration — every applied op is pushed onto the undo stack like a normal edit (the 50-entry UI cap applies as usual). Undo/redo semantics are unchanged; after applying, the user can undo the whole overlay piece by piece.
  • Rebase — because applied ops join the edit log, saving .arkdelta again right after applying produces an updated overlay against the new base (rebase = re-save).
  • Position overrides (session-only) — the review UI can resolve position collisions (ADD_ROOM/MOVE_ROOM onto an occupied cell) with a replacement position chosen by deterministic autopositioning or manual placement. Such overrides are an apply-time, per-session decision: they never enter the file format. They are re-validated against the live map immediately before commit (an occupied replacement cell skips the op with a reason, no data is overwritten), and the effective coordinates land in the edit log — so a subsequent rebase exports an overlay that already carries the corrected positions.
Base mismatch: applying onto a different map version is supported by design — operations whose targets no longer exist are skipped with reasons, everything else applies. Geometry review tooling (review window, ghost preview, collision autopositioning) is layered on top of this clean apply path.

10. Versioning & Compatibility

  • format_version is bumped only on incompatible changes to the envelope or operation schemas.
  • A reader refuses files with an unknown format_version (fail-closed) rather than guessing.
  • New operation types may be introduced within a format version only if old readers refuse them cleanly — which they do, via the schema check (unknown type ⇒ file refused). Producers must therefore treat adding an op type as effectively requiring a version bump for interoperability.

11. Complete Example

A delta with three operations: a new area, a new room inside it, and an exit from an existing room (100) into the new room. (Whitespace abridged; real files use the canonical writer.)

{
  "meta": {
    "format": "arkdelta",
    "format_version": 1,
    "ops_count": 3,
    "base": { "crc": "3f8a21c0", "version": "0.205.0", "revision": "0123456789abcdef…" },
    "app_version": "v1.6.0"
  },
  "ops": [
    { "seq": 1, "type": "ADD_AREA",
      "target": { "areaId": "d:1" },
      "payload": { "area": { "id": "d:1", "name": "Nowy obszar" } },
      "label": "Dodanie obszaru \"Nowy obszar\"" },
    { "seq": 2, "type": "ADD_ROOM",
      "target": { "roomId": "d:2", "areaId": "d:1" },
      "payload": { "room": { "id": "d:2", "x": 12, "y": -4, "z": 0, "name": "Polana", "env": 262 } },
      "label": "Dodanie pokoju \"Polana\"" },
    { "seq": 3, "type": "ADD_EXIT",
      "target": { "sourceId": 100, "dir": "n" },
      "payload": { "targetId": "d:2", "bidirectional": true },
      "label": "Dodanie wyjścia #100 n" }
  ],
  "checksums": {
    "file": "91c04d2e",
    "ops": [ "0a1b2c3d", "4e5f6071", "8293a4b5" ]
  }
}

On apply onto a map whose highest room ID is 6400 and highest area ID is 120: the area becomes 121, the room becomes 6401, and room 100 gains exit n → 6401 (with the reverse s → 100 on the new room, because bidirectional).
