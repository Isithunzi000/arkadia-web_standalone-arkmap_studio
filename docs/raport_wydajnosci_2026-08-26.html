  • Pierwszy draw jest płaski względem rozmiaru mapy (9–18 ms) — draw kosztuje tyle, ile widać w viewportcie (culling), nie ile ma mapa.
  • Najwyższe p95 kamery: 32,6 ms (stress_16x .arkmap). kryterium JANK (50 ms) nie złamane nigdzie w zmierzonym zakresie.
  • Headless renderuje programowo (SwiftShader) — na prawdziwym GPU użytkownika czasy będą niższe.

6. Metodologia

  • Baza: produkcyjny fixture map_master3.dat (60 obszarów, 26 988 pokoi) → base.arkmap przez tools/dat2arkmap.mjs.
  • Drabinka syntetyków: deterministyczne klony ×2/×4/×8/×16/×32 (przesunięcia współrzędnych, remap id blokami, sumy v4 (XXH3-64) liczone funkcjami aplikacji; walidacja validate() fail-closed po generacji).
  • Faza Node (bench_parse.js): kod parserów wyekstrahowany verbatim z arkmap_studio.html, 20 przebiegów + 3 rozgrzewki, --expose-gc, statystyki min/med/p95/max.
  • Faza przeglądarka (perf_driver.html + cdp_run.py): pełna aplikacja w iframe, zimne ładowanie co przebieg (cache-buster), prawdziwy zegar przez Chrome DevTools Protocol (bez virtual-time), heap z --enable-precise-memory-info, kamera = 40 synchronicznych draw() na ścieżce 5×8, świeży profil przeglądarki na przebieg (bez dyskowego cache).
  • Asymetria celowa: .dat ładuje się bez verifyChecksums (tak robi aplikacja — plik binarny traktowany jako zaufany), .arkmap z pełną weryfikacją. Pomiar odzwierciedla zachowanie produkcyjne 1:1.
  • Surowe dane: tests/perf/results/; ten raport: node tests/perf/report_build.mjs; własny przebieg: bash tests/perf/run.sh (README w tests/perf/).
